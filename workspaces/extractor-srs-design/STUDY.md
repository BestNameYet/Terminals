[O] Only the two transcript files are copied to Git; the four capture files are Actions artifacts with 30-day configured retention. ### 2.4 Older StateMachines linear exporter

[O] The older script untrusted AI/extract-shared-chat.js decodes an indexed React Router payload into a broad conversation object, finds loaderData or a structurally similar conversation object, validates a nonempty linear_conversation and exports the decoded object. [O] The accompanying inspect-current-shared-chat.yml iterates linear_conversation in array order to project indices, node IDs, parent, author, timestamps, recipient, model, content types and text or JSON-formatted content.

## 4. Structural extraction alternatives

### A. Browser rendering, OCR or DOM-only scraping

This is not supported as a preferred method by the documented working extractors. It adds browser automation overhead, can hide non-visible message metadata, and makes stable ordering and completeness difficult to establish. It might eventually be useful as an **independent human-visual fidelity comparison**, but shall not be the authoritative extraction algorithm.

### B. Execute inline scripts to recover decoded object

The older linear exporter proves that a decoded object with linear_conversation can be obtained from captured HTML. Its vm execution strategy violates the new security boundary. Running untrusted JavaScript is rejected even when Node vm creates a separate context; the relevant contract is **no downloaded code evaluation**.

### C. Nonexecuting indexed-table decoder plus selected parent chain

This is the most directly demonstrated current production algorithm. It reconstructs the selected visible branch from mapping/current_node and parent edges, detects missing parents/cycles and preserves a meaningful user/assistant text sequence. It does not preserve tool/internal, non-text, or alternate-lineage material and must not be labeled a complete raw conversation.

### D. Nonexecuting indexed-table decoder plus direct linear array

This uses source-provided linear_conversation order directly, preserving each original index and original node data. It covers roles, parts, and metadata beyond the selected visible transcript. It is semantically a different output: linear nodes are not guaranteed to be identical to the ancestry-selected branch or to exhaust every alternate branch. Missing/empty linear array must be an explicit failure for a linear-conversation export, not an invitation to relabel ancestry output.

### E. **Selected composite: decode once, produce two independently labeled projections**

[D] Fetch the original HTML **once** and parse its recognized React Router serialization **once** using a bounded, memoized, nonexecuting resolver. From that shared parsed representation, generate:

1. **Full linear capture** — linear_conversation entries in exact source index order, normalized with raw node/message data retained. This is the authoritative record for linear extraction. Absence/emptiness is a documented failure.
2. **Selected visible-branch projection** — mapping/current_node ancestry reconstructed and filtered exactly for visible text. This is the authoritative record for selected-view Markdown/JSON. Its chronology is defined by ancestry, not by linear order.
3. **Comparison and diagnostics** — counts, inclusion/exclusion reasons, missing-message records, ordered IDs and differences between representations. Differences are reported rather than silently corrected or treated as proof of corruption.
4. **Raw capture and receipt** — original HTML, complete decoded conversation, hashes, source/workflow provenance, and an external final readback attestation.

Both products share the same one-pass source acquisition and decoder infrastructure, but they **must not share a false global ordering assumption**. If either mandatory representation is unavailable, the overall complete-export status is FAILED; any partial diagnostic files may remain in an artifact clearly labeled incomplete. There is no silent fallback from linear to ancestry and no silent conversion of the ancestry-selected path to linear.

## 5. Efficiency analysis and chosen optimization

Let B = HTML bytes, S = indexed serialization slots, L = linear nodes, M = mapping nodes, and P = selected parent-chain length. One network fetch and one decoding pass cost O(B + S); independent linear iteration costs O(L); indexed mapping build and branch walk cost O(M + P). The composite therefore targets **O(B + S + L + M + P) time** with bounded storage dominated by the retained source and decoded graph; it does not multiply the network transfer or parsing passes by two. It is not legitimate to call direct-linear iteration asymptotically faster than selected-branch traversal: both are normally linear in their own node sets.

Efficiency measures: stream and cap the body before concatenation; keep exact original response bytes; decode recognized string payloads without evaluating code; memoize indexed-reference resolution and detect reference cycles; avoid repeatedly deep-copying a decoded graph; cache structural lookups when feasible; derive Markdown from a normalized visible record array rather than re-traversing HTML; hash files using exact bytes; compute cross-representation comparison from stable IDs and indices; validate before Git staging; serialize publication operations that target main.

Not justified: dynamically fetching mutable parser code at runtime; sorting nodes by timestamp; using a tag index or pre-extracted transcript as primary source; running both repositories' entire builders independently; treating an Actions artifact as proof of Git persistence; or assuming that only one field name/HTML version will exist forever.

## 6. Chosen dispatch and write-path contract

[D] Preserve the existing manual-dispatch.yml identifier and legacy target_url/write_path compatibility. Add an optional **request_json** string input. It holds the JSON object from an operator-supplied local file; this avoids requiring a root committed request file. Exactly one request form is active: request_json OR legacy target_url/write_path. Explicit mixed modes are rejected.

Canonical JSON request fields: target_url (required); write_path (optional template, default workspaces/shared-conversations/{share_uuid}/{run_id}-{run_attempt}); request_id (optional correlation); export_profile (default complete). This default is a **template**, not the current fixed-sample-UUID YAML value. Placeholder substitution happens only after URL validation in the workflow; valid placeholders are share_uuid, run_id, run_attempt. The resolved path is restricted beneath workspaces/shared-conversations, with run-specific isolation. A valid explicit path still must satisfy workspace controls and collision policy.

The terminal receives immediate dispatch acknowledgment only. GitHub Actions generates the actual run receipt. The terminal or an independent observer must correlate to a specific run ID, monitor its conclusion, and verify the final remote readback before reporting VERIFIED.

## 7. Products, privacy and provenance

[D] The complete profile generates response.html, conversation-raw.json, linear-conversation.json, conversation.json, conversation.md, diagnostics.json, receipt.json, and execution.json in one run-scoped directory. conversation.json and conversation.md are expressly the selected-visible projection; linear-conversation.json is expressly source-linear; conversation-raw.json retains the broader decoded conversation. Raw nodes, tool/internal roles, nontext content and metadata are preserved structurally and not fabricated as text. The complete profile commits the eight files to the validated Git path and also uploads an Actions artifact. **The repository must remain access controlled** because raw HTML and decoded metadata can be sensitive despite originating from a public share URL. No token/header secrets shall be included in logs or outputs.

The receipt records exact data-file bytes, SHA-256 hashes, source ID, run ID/attempt, parser revision and method names. It does not hash itself or the mutable execution record. execution.json records pre-publication evidence; final verified commit SHA, remote readback results and completion status belong in an **external final Actions attestation** and step summary to avoid a circular self-hash or self-referential commit-SHA claim. A repository commit without this final attestation is not an accepted complete export.

[D] If long-term complete raw retention in Git is later disallowed by privacy policy, a separate profile can place raw HTML/decoded data solely in restricted artifacts. Such a change must be explicit and cannot silently substitute a reduced product for this complete baseline.

## 8. Publication, concurrency and rollback policy

[D] After validation and regression, copy only generated allowlisted files into the run-scoped destination. Confirm no preexisting path segment or leaf file is an unsafe symlink; reject prohibited paths and disallowed collision with another source/run. Stage exactly those files, plus only any inventory file actually documented for Terminals. Run-specific paths prevent two exports of the same source from clobbering one another; publication to main is serialized with cancel-in-progress false. Commit only when changes exist. On a competing main update, fetch/rebase and attempt a bounded retry (three total push attempts is the StateMachines precedent). Reject non-fast-forward/lost-update outcomes. After push, fetch the remote main ref and compare every required committed output against local bytes and SHA-256. Publication is VERIFIED only when **all** required files match and the mandatory pipeline completed.

A failed run may leave an Actions artifact or a partially published Git commit. It must not claim transactional rollback that Git does not provide. The execution receipt must distinguish not-published, partially-published and verified-published states. A later cleanup is a separate auditable operation, not an implied automatic reversal.

## 10. Conclusions and delivery boundary

**Decision:** Implement one workflow-dispatched Node.js extraction pipeline that reads a JSON request (with legacy CLI compatibility), fetches and parses once, preserves source linear order for a complete structured product, independently reconstructs the selected visible parent chain, renders both without conflating their chronologies, and commits verified outputs to a run-specific templated workspace path.

This is the chosen target design for the accompanying final SRS. The study and SRS are completed documentation; extraction implementation, dispatch permission changes, actual acceptance test execution and production readback proof remain separate future engineering deliverables. Every source comment is retained verbatim for audit and alternative-design comparison.
